# 段階2c 計画（サーボキャリブ。2026-11-11 承認版）

目的: 脱力 → 中央 → MIN/MAX の手順で、EEPROM の `Homing_Offset` と `Min/Max_Position_Limit` を書き、yaml に保存する。LeRobot のコードにもキャリブファイルにも依存しない。
規則: 実機（シリアルポートを開く操作を含む。EEPROM の読み出しも）を動かすのはユーザーだけ。Claude は偽サーボ（pty）までを実行する。EEPROM への最初の書き込み（C0.5）の前に、ユーザーの確認を取る。

## 1. 設計
- 新パッケージ `so_arm101_calibration`（C++ の CLI）。`so_arm101_hardware` の `so_arm101_sts3215` ライブラリを再利用する。実行中は ros2_control を止める（ポートの占有）。
- コマンド（すべて既定は書き込みなし。書き込みは `--write` と確認文字列 `WRITE-EEPROM` の手入力の両方が必要）:
  - `eeprom_backup`: 読み取り専用。全関節の EEPROM（アドレス 0〜39 の生バイトとデコード値）を `~/so_arm101_check/eeprom_backup_<日時>.json` に保存し、読み直して一致を確認する。保存できなければ中止。
  - `measure`: **測定。EEPROM には書かない**（書くのは SRAM の `Torque_Enable=0` だけ。`Lock` は書かない）。結果を測定ファイル（`~/so_arm101_check/measure_<日時>.json`）に保存する。
  - `apply`: **適用。測定ファイルから `--write` で書く**。
  - `restore`: バックアップから戻す（書くのは Homing_Offset と Min/Max の 3 項目だけ）。既定は dry-run。
- 測定ファイルの内容: 関節ごとに、中央姿勢の生のエンコーダ値（actual）、測定した時点の Homing_Offset、計算した新しい Homing_Offset（`actual − 2047`）、記録した min/max（actual と新座標の両方）、center、日時、ツールのバージョン、測定時のバックアップのファイル名。
- 測定の式: `actual = present + 現在の Homing_Offset (mod 4096)`。`reset_calibration`（0/0/4095 の中間書き込み）はしない。MIN/MAX の記録はソフト側で新しい offset を当てて計算し、wrist_roll は `mod 4096` で展開する。
- 検査（測定の終わりと適用の前に行い、満たさなければ書かない）: min < max、各関節の幅が下限（既定 200 tick）以上、新座標で 0〜4095 に収まる、`|Homing_Offset| ≤ 2047`（bit11。+2048 は書かずに中止）。
- **適用の前提**: (a) 今の EEPROM（全関節の 3 レジスタ）が、指定したバックアップと一致している（違えば書かない）。(b) 測定ファイルの「測定した時点の Homing_Offset」が今の EEPROM と一致している（actual の計算の前提）。(c) 全関節 PING 応答あり、機種番号 777、Torque_Enable=0 を読み戻し確認。
- 適用の書き込み: 関節ごとに Lock=0 → Homing_Offset → Min → Max → Lock=1。1 項目ごとに「待つ → 読み戻し」。`--joints` で関節を絞れる。**yaml を更新するのは 6 関節すべてを 1 回の適用で書いたときだけ**（1 回だけ、一時ファイルに書いて rename）。関節を絞った適用（C2）では yaml を更新しない。
- D1: 0 rad は LeRobot と同じ「記録した範囲の中央」（`center = (min+max)/2`）。D3: `angle_ticks: 4095` のまま（中央から ±1900 tick の端で約 0.041°、約 0.0007 rad の差）。
- D2: 2c では記録した範囲をそのまま EEPROM に書く。URDF の範囲には絞らない（`--clamp-to-urdf` は作らない）。理由: 位置が limit の外にある状態でトルクを ON にすると急に動くおそれがある（推測）。出発点の姿勢の elbow は URDF 上限まで 0.02 rad。絞るかは C4 の後に別途決める。

## 2. 失敗時の動き
- 書き込みの途中で失敗したら、**その回で書いた全関節**をバックアップの値に戻そうとする（3 項目を 1 項目ずつ、書く → 待つ → 読み戻し。戻せない項目があっても残りは続ける）。
- その後、全関節・全 3 レジスタを読み直し、状態を **旧（バックアップと一致）／新（書こうとした値と一致）／不明（どちらでもない、または読めない）** に分けて表で表示する。
- 戻せなかった項目があれば、バックアップのファイル名、`restore --write` のコマンド例、「yaml は更新していない」こと、「この状態で書き込みモードの launch を起動しない」注意を表示する。
- 終了コード: 0=全成功 / 1=失敗したが全関節が旧に戻った / 2=一部が新または不明のまま、または Lock=1 を確認できなかった / 3=バックアップや前提の確認の失敗（何も書いていない）/ 4=入力・検査の不合格（何も書いていない）。
- **Lock=1 の書き込みに失敗したとき**: 通信エラーのときだけ 3 回再試行。それでも失敗したら `ERROR: Lock=1 NOT confirmed on <関節>（EEPROM は書き換え可能なまま）` を表示し、終了コード 2。**対処は「サーボの電源を入れ直す」**（Lock は SRAM で、電源投入時の既定値は 1。実機で確認済み: inventory の確定した事実）。電源を入れ直した後、読み取り専用で起動して診断の `lock=1` を確認する。
- yaml は、失敗した回では書かない。
- 先に書き終わった関節が新しいまま残り yaml が古い状態: 書き込みモードの起動を**拒否する**（2c-1a。読み取り専用は WARN のまま。拒否を外すスイッチは付けない）。

## 3. 読み戻しと再試行
- 再試行は通信エラー（無応答、チェックサム不一致、ヘッダ不正）のときだけ、最大 3 回。**値の不一致は再試行せず、すぐ失敗**。
- EEPROM に書いた後は、決めた時間だけ待ってから読み戻す。既定 50 ms（仮置き。根拠なし）。`--eeprom-wait-ms <ms>`（0〜1000）で変えられる。
- C0.5 で実測して決める（5 章）。

## 4. 診断の変更（2c-1a、承認済み）
- 事実（コード）: `run_diagnostics()` は EEPROM と yaml の不一致を WARN で出すだけで、`fatal` は「読み取りの失敗」と「機種番号が 777 でない」だけ。書き込みモードでも不一致のまま起動する。
- 変更: **書き込みモード（`read_only:=false`）のときだけ、不一致で `on_configure` をエラーにする**（トルクは ON にならない）。読み取り専用は WARN のまま。解除のスイッチは付けない。

### C0.5 の合格基準（明記）
- バックアップと同じ値の書き戻しが、読み戻しまで一致して成功する（終了コード 0）。
- 待ち時間の実測: `--eeprom-wait-ms 0` などで**読み戻しが一致しなかった場合は、失敗として扱われ、戻す処理が走り、終了コードは 1 になる。これは想定どおり（不合格ではない）**。書いた値はバックアップと同じなので、戻す処理の後も全関節が「旧」であることを確認する。一致する最小の待ち時間を探し、その 2〜3 倍を既定にする。
- 同じ値の書き込みでは「値が変わった」ことを待ち時間では確かめられない。C0.5 では通信エラーの有無と応答のタイミングを見て、値が変わる状況での確認は C2 で各項目の読み戻しの一致として記録する。

### C3 の URDF リミットとの比較（URDF・SRDF は変えない）
- 出す表（関節ごと）: 新座標での各姿勢（出発点、折りたたみ姿勢）の値と、**URDF の上限・下限までの残り（rad）**。記録した範囲の両端（rad）が URDF の範囲の内側か外側か。
- 範囲の外、または余裕が小さい関節（目安 0.05 rad 未満。目安は報告のための仮の値）があれば、**C4 の前にユーザーへ報告して判断を仰ぐ**。
- 計算は `tools/` のオフライン スクリプト（シリアルを開かない）。URDF の値は読むだけ。

## 6. 偽サーボでの試験の範囲
- `tools/fake_sts3215.py` と `test/fake_servo.hpp` に、EEPROM メモリ、Lock による EEPROM 書き込み拒否、書き込み途中の中断、エラー挿入（無応答、チェックサム不一致、ERR ビット、読み戻し不一致）を追加。
- 試験: 測定（再現性、wrap をまたぐ roll）、適用（正常、前提の不一致で拒否、yaml は 6 関節のときだけ更新）、失敗時の復元（各項目の失敗、途中の中断、Lock=1 の失敗）、終了コード、旧/新/不明の表示、バックアップ・測定ファイルの破損（JSON 破損、機種番号違い、ID の欠け、範囲外の値）で書かずに止まること、bit11 の境界（±2047、±2048、0）。
- **復元の試験は 2 段階**: 偽サーボ（2c-2。実機の前）と、実機で新しい値を書く前（C0.5）。実機ではさらに C2 で復元を通す。
- 偽サーボで確認できないこと: Lock の実動作と EEPROM の書き込み待ち時間、Min/Max limit が Present_Position の読み値に影響しないこと（推測）、負の offset の実機での挙動、実際の脱力。

## 8. LeRobot との違いと出典
- 式・レジスタ・順序の考え方は LeRobot 0.4.2（`so101_follower.calibrate()`、`motors_bus.py`、`feetech.py`）と同じ。コードはコピーせず再実装する。出典とライセンス（Apache-2.0）を実装時に `docs/third_party.md` に追記する。
- 違い: 中間の 0/0/4095 を書かない／測定と適用を分け、測定ファイルを残す／適用の前にバックアップとの一致を確認／書き込みは各項目を読み戻し／失敗時は全関節を戻す／終了時に Lock=1／dry-run 既定／yaml は成功後に 1 回だけ。
