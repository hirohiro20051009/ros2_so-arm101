## 2. 補正値の持ち方

### 2.1 キー・単位・既定

- キー名: `zero_offset_deg`。関節ごと（`joints.<名前>` の中）。単位は**度**。符号: 真の角度 = (direction × (raw − center) × 360 / angle_ticks) + `zero_offset_deg`（つまり direction を掛けた**後**に足す。δ は真の角度の座標の量）。
- 既定 0。キーが無い関節は 0 として読む（今の yaml がそのまま読める。`schema_version` は 1 のまま）。
- 対象は `kind: angle` の関節だけ。`linear_percent`（gripper）に 0 以外を書いたら、読み込みでエラーにする。
- 読み込みの検査（推測の値）: 有限であること、絶対値が 15° 以内（打ち間違いを止める。elbow の候補は 6〜7°）。**（2026-11-16 変更: ユーザーの決定で 10° 以内にした。J1 で実装。理由は `inventory.md` の J1 の節）**
- 単位を度にする理由（推測）: 物差し・当てはめの結果・docs がすべて度。rad にすると 0.1 rad のような丸めた値と取り違えやすい。tick にすると angle_ticks（4095 か 4096 か未決。`follower_calibration.yaml:12` のコメント）に依存して値が変わる。

yaml の書き方の例（elbow だけ書く。値は例で、5 章で決める）:

```
elbow_flex: {id: 3, kind: angle, direction: 1, center: 1969.5, zero_offset_deg: -6.31, min: 849, max: 3090, eeprom: {...}}
```

### 2.2 apply が yaml を作り直しても消えない仕組み

- 事実: apply は `render_calibration_yaml`（`apply.cpp:55-90`）で、古い yaml から id・kind・direction だけを引き継ぎ、center・min・max・eeprom を新しく書く。ほかのキーは書かないので、補正値は消える。ヘッダのコメントも固定の文面で作り直す（`apply.cpp:57-59`）。
- 案（推奨）: `render_calibration_yaml` が、古い yaml の `zero_offset_deg` を読み、**キーがあった関節は同じ値を書く**。キーが無かった関節は書かない（今の出力と同じ）。`update_calibration_yaml`（`apply.cpp:95-`）の読み直しの検査に「古い yaml の補正値と、新しい yaml の補正値が全関節で同じ」を足す。
- 試験: 補正値あり・無しの古い yaml から apply の出力を作り、(i) 補正値が同じ、(ii) 無かった関節にキーが増えない、(iii) 選択した関節だけの apply でも全関節の補正値が残る。
  - **注記（2026-11-16、J3 でユーザー承認）**: 上の (iii)「選択した関節だけの apply でも全関節の補正値が残る」は成り立たない。一部の関節だけの apply は yaml を更新しない（`apply.cpp` の「一部の関節だけを書く。yaml は更新しない」）。(iii) は「**一部の関節だけの apply では yaml は変わらない**」に置き換えた（試験 `AGroupApplyLeavesAYamlWithAnOffsetUnchanged`）。元の記述は上に残す。
- 変えない: eeprom 欄（`homing_offset`・`min_limit`・`max_limit`）は今までどおり。補正値は EEPROM に関係しない。
- 注意（推測）: コメントは apply のたびに固定の文面になる。補正値の由来（日付・方法・材料の sha256）は yaml のコメントに頼らず、`inventory.md` に書く（元の yaml の内容を控える決まりにも合う）。

### 2.3 再校正のときの補正値の意味（要判断）

- 推測: 0 rad の位置 = center = (Min+Max)/2 は、測った範囲の中央。δ はこの中央から URDF の 0 までの角度。範囲の両端は機械の当たりで決まるので、再校正でも約 ±数 tick で再現する（`so_arm101_calib compare` で見られる）。このとき δ はそのまま使える。
- 範囲の端の測定がずれる（例: 片側が当たらない）と、center が動き、δ との組が合わなくなる。実用上は apply の直後に 7 章の確かめ（出発点の物差し）を 1 回やる。
- 案: 持ち越しは「値をそのまま」。center が今の値から 10 tick（約 0.9°）以上動いた関節は、apply が警告を出す（推測の値。決定の表の項目 9）。

### 2.4 [diag] と eeprom 欄への影響

（J2 で実装済み: 起動の INFO は δ ≠ 0 の関節ごとに 1 行にまとめ、実効の許容も同じ行に入れた。式と文面は inventory.md の J2 の節。）

- 補正値は EEPROM と無関係なので、**MATCH／MISMATCH の判定に入れない**。
- 追加（案）: 起動時に、補正値が 0 でない関節について INFO を 1 行出す: 例 `zero_offset_deg: elbow_flex -6.31 deg (the reported position is the measured position plus this)`。[diag] の行そのものは変えない（既存の試験・ログの形を保つ）。
- 追加（案）: 実効の許容（4 章の案 B）を、変えた関節だけ INFO で出す。

### 3.4 補正が二重にかからないこと

- 補正が入るのは `raw_to_rad` と `rad_to_raw` の 2 関数だけで、読みと書きで**逆の向き**に 1 回ずつ（読み: +δ。書き: −δ）。
- `/joint_states` から先（ik・camera・RViz）は δ を知らない。そこで δ を足さない（足すと二重）。例外は `pose_margin.py`（yaml を直接読む。上の表）。
- 守りとして、`raw_to_rad(rad_to_raw(x)) == x`（丸めの範囲で）の試験を、δ ≠ 0 の関節で行う。片方だけに入れた場合（8 章の守りを外す確認）に落ちる。

### 3.5 モックへの影響

- 事実: モックは yaml を読まない。補正の有無でモックの挙動は変わらない。bringup のモックの試験（47 件）・ik のモックの通しに影響しない。
- 推測（リスク）: モックでは補正が効かないので、補正に関する不具合はモックで見つからない。補正の試験は、ドライバの単体の試験（偽のバスを使う `test_sts3215_system.cpp`）と実機の確認で受け持つ。
- 案（今回はやらない）: モックの `initial_positions.yaml` や SRDF の名前付き姿勢（`center`・`home`・`initial`）は「真の角度」のまま。実機では補正後に物理的な姿勢が変わる（7 章）。

## 4. 範囲の扱い（rad で見た elbow の範囲がずれる）

### 4.1 事実と計算

- 事実: elbow の yaml は center 1969.5、min 849、max 3090、angle_ticks 4095（`follower_calibration.yaml:20`）。1 tick = 360/4095 = 0.0879°。
- 計算: raw の範囲は center から ±1120.5 tick = ±98.50°。URDF の上限は 1.69 rad = 96.83°（`so101_new_calib.urdf:399`。`analytic_ik.py:71-72` の `Q_MIN`・`Q_MAX` も同じ）。
- 計算: 補正後の真の範囲は 上側 = 98.50 + δ、下側 = −98.50 + δ（度）。

| δ（度） | 真の範囲（下から上） | URDF の上限（96.83°）の超過 | 超過の tick | 許容 50 tick との関係 |
|---|---|---|---|---|
| −5.77（物差し） | −104.27 から +92.73 | 4.10° | 46.6 | 許容の内側 |
| −6.07 | −104.57 から +92.43 | 4.40° | 50.0 | ちょうど境目 |
| −6.31（(g)） | −104.81 から +92.19 | 4.64° | 52.8 | 許容を超える |
| −6.77（RMS 最小） | −105.27 から +91.73 | 5.10° | 58.0 | 許容を超える |

- 事実: URDF の下限（−96.83°）に対する余裕は、どの δ でも約 7〜8° ある（下側の真の範囲が −104° 台）。上側だけが足りなくなる。
- 事実: 異常の判定は `want > raw_max + 50`（`sts3215_system.cpp:970`、`kClampToleranceTicks = 50`、`sts3215_system.hpp:40`）。異常が `anomaly_cycles_` 回続くと `set_fault`（`:897-907`）。**Goal_Position の送信が止まり、トルクはそのまま**（腕は落ちない。再起動か deactivate→activate で回復）。50 tick 以内なら黙ってクランプ（`:971`）。
- 推測: 異常にならなくても、クランプされたまま腕が URDF の上限の手前（約 4〜5°）で止まる。MoveIt は上限に着いたつもりで進む。`ros2_controllers.yaml` の先頭 50 行には目標の許容（constraints）の設定が無く、軌道の完了判定への影響は未確認（実装の前に残りの行を読む）。

### 4.2 案

| 案 | 内容 | 良い点 | 悪い点 |
|---|---|---|---|
| A | 何もしない | 変更なし | δ が −6.07° より負だと、URDF の上限まで計画した指令が異常になり、fault（送信停止）。RViz で上限近くを選ぶと止まる。止まっても腕は保持 |
| B | ドライバの許容を、補正で範囲が縮む側だけ、縮んだ分（tick）だけ広げる（許容 = 50 + 縮み。縮みは、δ が負なら上側、正なら下側の ceil(abs(δ)×4095/360)） | 補正後も「URDF の端まで計画できる」。新しいキーが要らない。δ を変えても追従する | 異常の検出がその側だけ緩む（δ = −6.77° で上側 127 tick = 11°）。クランプ自体は raw_max で効くので、サーボが raw の範囲を出ることは無い |
| C | yaml に関節ごとの許容のキー（例 `clamp_tolerance_ticks`、既定 50）を足し、elbow だけ手で決める | 値が見える。δ に依存しない | キーが増える。δ を変えて許容を直し忘れる |
| D | URDF の上限を狭める | 計画が実機の範囲に収まる | **URDF・リミットは変えない決まり**。採らない |
